System design — draft

Tabletop Judge

A phone-and-shared-screen build of Cards Against Humanity: a host server, room codes, phones as hands, and an optional shared display for the table.

Roles, not devices

One web app; the role is chosen at join time, not baked into the build.

Every connected client is one of three roles in the same room. None of them are separate apps — a phone and a tablet load the same page and just present differently depending on which role was picked at join.

Role · Phone
Player
Holds a hand of white cards, sees the current black card, submits face-down (ordered, for pick-2/pick-3), sees the scoreboard.
Role · Rotates
Card Czar
Not a separate client — whichever player's turn it is gets Czar-only UI on their own phone: reveal submissions, pick the winner.
Role · Optional
Table
Tablet, laptop, or TV. No hand of its own — shows the black card large, shows submissions face-down, mirrors whoever is currently Czar.

The Table doesn't belong to a player

Rather than manually "passing" the tablet, the Table client auto-follows the active Czar each round — the server just tells it whose reveal/pick view to mirror. That matches how the physical game works: the deck sits in the middle, and whoever's turn it is reads from it. If the current Czar would rather use the shared screen than fumble their own phone, the same reveal/pick controls work from either surface — the Table is a mirror, not a separate source of truth.

Room lifecycle & pairing

Short codes, persistent seats, no lost hands on a locked phone.

Host creates room→ Room code generated→ Players + Table join with code→ Host picks packs, starts
  • Room code: 4–6 characters, letters/digits only, excluding visually ambiguous ones (0/O, 1/I) — read out loud or typed on a phone keyboard without confusion.
  • Join flow: enter the code, pick a name, pick a role (Player or Table). The server hands back a persistent client token, stored on-device, distinct from the room code.
  • Reconnects: that token is what actually matters. A phone that locks, backgrounds, or drops wifi mid-round reconnects to the same seat and hand automatically — the room code alone doesn't guarantee that, so it's treated as a separate concern from day one rather than patched in later.
  • Table doesn't take a seat: it joins the room but never enters the player rotation or holds cards.

Card data

Built from the supplied cah-cards-full.json — 427 packs, official CAH plus third-party.

The source file is an array of packs, each with a name, an official/third-party flag, and its own white and black cards:

[{
  "name": "Cards Against Humanity: Big Bad Bundle",
  "official": true,
  "sheetName": "CAH A Few Extra",
  "white": [
    { "text": "My private island.", "pack": "107" }
  ],
  "black": [
    { "text": "There must be more to life than _.", "pick": 1, "pack": "107" }
  ]
}]

Blanks on black cards are marked with a single _; pick is how many white cards fill them. Distribution across the file:

Deck build is per-room, not global

At room creation, the host is shown the pack list (name, official/third-party, card counts) and checks which ones to include — an "official only" shortcut plus the ability to add specific third-party packs. The server merges the selected packs' white and black cards into that room's deck at start time. Swapping or upgrading cah-cards-full.json later just changes what shows up in the picker; it isn't wired into any client code.

Round flow

Server-authoritative state machine — clients render state and send intents, never resolve the round themselves.

1 Lobby→ 2 Dealing→ 3 Submission→ 4 Reveal→ 5 Judging→ 6 Round End

Round End loops back to Dealing until the game's win condition is hit, then falls through to Game End. A few of these steps carry real logic worth calling out:

  • Dealing: server tops every hand up to its target size from the room's shuffled white deck; reshuffles the discard pile back in if the deck runs dry.
  • Submission: for a pick-2/pick-3 black card, the player arranges their chosen cards in order client-side and submits an ordered array — the server enforces the count and preserves that order through to Reveal, since sequence changes the joke.
  • Reveal: submissions are shown anonymized and shuffled, never in submission order, so the Czar can't infer who played what from timing.
  • Judging: only the Czar's client (phone or Table, whichever they're using) can send the pick; the server rejects a pick from anyone else.

House rules

Each rule is a hook into the state machine — submission validation, dealing, or scoring — toggled per room at creation. Not special-cased inline, so adding the next one doesn't mean touching the core loop.

House rule
Rando Cardrissian
Each round, the server auto-submits one random white card from a virtual player who never wins or scores — pure chaos filler in the lineup. Hooks into Dealing (draws a card) and Submission (auto-fills it) only.
House rule
Double Down
Hooks into Submission, Judging, and Scoring — detailed below.

Double Down, resolved

  1. A player submits a white card as normal for the round.
  2. They're dealt a replacement immediately (not held back until Round End, so the new card is in hand while the round is still live).
  3. If they'd rather play that replacement instead, and they hold at least one black card won from a previous round, they can wager it — that spends one won black card as the stake.
  4. Wagering adds the replacement to the lineup as a second entry from the same player, alongside their original — not a swap. The Czar sees two anonymized cards from that player without knowing they're linked.
  5. If either of the two wins: the player keeps that round's black card and gets the wagered one back — a double-down pays for itself. If neither wins: the wagered black card is lost back to the box, on top of not winning the round.

Because the stake is a previously-won black card, a player can't double down before they've won at least once — the mechanic is load-bearing on scoring rather than a separate currency to track.

Suggested stack

Sized for the confirmed target: private games, a handful of concurrent rooms, not a public matchmaking service.

  • Backend: Node.js + WebSocket (Socket.io for its room/namespace handling), single process, in-memory room state. No database or Redis needed at this scale — room state can live and die with the process, and a restart just means restarting whatever game was in progress.
  • Frontend: one React app, role-aware from a query param or route (/room/ABCD?role=player vs ?role=table) rather than separate builds.
  • No native app: everything is mobile web — join via room code in a browser, same pattern as Jackbox/Kahoot, no App Store friction for a private game night.

Deployment

Node server on a home machine, Cloudflare Tunnel for the public URL, domain already on Cloudflare.

cloudflared on host machine→ named tunnel→ DNS CNAME → tunnel→ public hostname
  • Tunnel, not port forwarding: cloudflared runs on the same machine as the Node server and makes an outbound connection to Cloudflare — no router port forwarding, no exposed home IP. Cloudflare terminates TLS at the edge.
  • Setup shape: authenticate cloudflared against the Cloudflare account, create a named tunnel, point a subdomain at it with cloudflared tunnel route dns (e.g. cah.yourdomain.com), and give the tunnel a small config file mapping that hostname to the local Node port. Running it as a service (cloudflared service install) keeps it up across reboots.
  • WebSockets just work: Cloudflare Tunnel proxies the Upgrade handshake through to origin with no special config — Socket.io traffic passes through the same as plain HTTP.
  • URL stays open, no Cloudflare Access: the join screen is reachable by anyone with the link — no login wall in front of it, so a friend can tap the link and go straight to typing a room code. That shifts the actual security burden onto the room code itself:
    • Codes should be short-lived — expire or become unjoinable once a room starts (or after some idle timeout in the lobby), not valid indefinitely.
    • Worth rate-limiting join attempts per room code so guessing 4–6 characters isn't cheap.
    • Since it's a private-use target rather than public matchmaking, this is a reasonable trade — an unguessable code plus a short window is enough friction without making guests log in.
